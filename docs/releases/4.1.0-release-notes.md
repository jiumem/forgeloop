# Forgeloop 4.1.0

Forgeloop 4.1.0 统一了 Coder 与 Reviewer 的交付价值函数，并选择性吸收上游 Skills v1.2.3。核心目标是让审查继续发现真实缺陷，同时拒绝没有产品价值、没有正式权威或只追求技术完美的复杂化要求。

## 统一交付价值函数

- 正确性与证据可信度仍是硬约束；最小语义扰动只用于在多个完整可行方案之间选择，不能换取虚假 `PASS`；
- Spec Reviewer 保留对权限、失败、恢复、并发、跨模块不变量和证据可信度的完整检查能力，同时遵循“广泛检查、克制阻塞”；
- Blocking Spec Finding 必须连起批准结果、必要不变量、批准模型内的可达反例和 Candidate 的可观察失败；宽泛引用、未来拓扑、内部对称或更强技术保证不能单独成为阻塞理由；
- 未逐字声明但由批准结果必然推出的约束仍可阻塞，例如批准重试造成重复副作用、批准权限模型存在可达绕过、恢复路径误认残留事实或证据自我证明；
- Coder 在 Repair Diagnosis 中先独立证伪 Finding，再选择 `NO_REPAIR` 或最小完整修复，不再把 Reviewer 的复杂化建议直接当成需求。

## 上游 v1.2.3 选择性集成

- 上游固定版本升级到 `v1.2.3`，同步流程排除上游 `agents/openai.yaml`，由 Forgeloop 自己的 Skill 元数据保持唯一事实源；
- `diagnosing-bugs` 增加敏感信息脱敏边界；`codebase-design` 使用 Harness 中性措辞；架构改进加入 YAGNI 热点判断；TDD 补齐公开行为接缝的上游方法；
- `prototype` 在领域交互不确定性上优先使用单文件 HTML，在运行时语义不确定性上使用宿主原生探针，并明确不自动建分支、提交或写 Tracker；
- `wayfinder` 采用 Decision Ticket 语言，但不自动创建研究代理或研究分支；
- 不引入 Wizard、`to-questionnaire`、`wait-what` 和 `writing-for-agents` 等新入口，避免扩展套件表面积。

## Grilling 有界提问

- 每轮只提出 3–5 个彼此独立、真正影响决定的问题，硬上限为 5；
- 依赖前一个答案或具有高影响的问题单独提问，避免一次把长串互相耦合的问题压给用户；
- 支持整批接受默认建议，也允许退回逐题处理；
- 一旦形成最小完整设计即停止，不以穷尽所有技术可能性为完成标准。

## 兼容性与升级边界

- 4.1.0 不增加正式 Skill、用户入口、模型可调用能力、Event、Tracker Item 类型、持久化状态或 parser；
- 现有 Spec、Ticket、Run、Checkpoint 和 4.0.0 的修复预算语义保持兼容，不需要数据迁移；
- 4.0.0 的行为迁移边界仍见[3.6.1 → 4.0.0 迁移指南](../migrations/3.6.1-to-4.0.0.md)；
- 20 个正式 Skill、11 个用户入口和 9 个模型可调用能力保持不变。
