# 从 Forgeloop 4.2.1 升级到 4.3.0

4.3.0 是 `$run-initiative` 的运行模型迁移。它删除 4.2.x 的每 Ticket Scheduler、Coder、双 Reviewer 修复循环与 Acceptance Seal；升级后不能把旧 Checkpoint Event 当成 4.3.0 的活动执行状态。

## 升级前

1. 记录所有正在运行或暂停的 `$run-initiative` 工作项、分支、Commits、PR/MR 和当前检查结果。
2. 不要删除 4.2.x 的 Issue Comments、Notes 或本地 Agent Run 记录；它们仍是历史证据。
3. 若必须继续完全相同的旧协议，请在隔离环境中固定使用 4.2.1。不要让两个版本同时推进同一工作项。

## 选择 4.3.0 交付形态

- 大 Ticket：仅当一个 Ticket 达到 Spec 级复杂度、确实需要多个连贯 Slices 时使用。
- Spec：默认正式交付形态。Spec 的 Tickets 直接成为一个交付分支上的 Slices。
- 有界 Initiative：一个 Initiative 可以包含多个 Specs；每个 Spec 一个分支和一个 PR，并复用同一对 Reviewer 任务。
- 小 Ticket：直接实现，不调用 `$run-initiative`。
- 多个 Initiatives：拆开执行，不合并为一次运行。

## 迁移活动工作

4.3.0 不自动转换旧运行。对每个未完成工作项：

1. 保留旧分支和 Tracker 历史，不重写或伪造旧事件。
2. 从当前正式 Ticket、Spec 或 Initiative 重新确认批准 Scope、目标分支、Integration Policy、验收结果和剩余工作。
3. 新建或恢复一个符合 4.3.0 的交付分支。不要把与所选交付单元无关的旧改动吸收进去。
4. 把已完成的真实 Commits 映射到新 Slices；已经满足结果但无需代码变化的项记录为 `NO_CHANGE_REQUIRED` 及其可观察证据。
5. 对完整分支只运行一次双轴 Review。不要导入旧 Reviewer Verdict、repair round 或 budget 作为新的控制状态。
6. 将新 Review 报告和每个 Finding 的处置写入所选 Tracker 工作项，再运行最终 Gate 和单一 PR。

如果无法可靠确定旧工作对应的批准 Scope、当前 Head 或完成证据，保持分支不动并返回 `BLOCKED`；不要猜测或通过空 Commit 补齐历史。

## Review 行为变化

- 删除 `Under 400 words` 限制；
- Reviewer 仍然全面检查，但只报告影响当前交付判断的问题；
- Review 不再返回合并 Verdict，也不在修复后重复运行；
- Delivery Worker 对 Findings 独立记录 `FIXED`、`REJECTED` 或 `CONTRACT_BLOCKER`；
- 最终 Gate 与仓库 Integration Policy 决定交付分支能否进入 PR 和合并路径。

## 已删除的运行协议

以下 4.2.x 概念不再存在于活动插件中：

- `RUN_CLAIMED`、`CODER_RESULT`、`REVIEW_RESULT`、`RUN_PAUSED`、`RUN_RESUMED` 等运行 Event；
- `cycle_anchor`、三轮 repair budget、Cycle 1/Cycle 2 和 automatic renewal；
- per-Ticket branch、Reviewer Verdict、重复双审和 Final Acceptance Seal；
- `SHARED`/`CUMULATIVE_AUDIT` Final Integration Gate；
- 由 `$run-initiative` 自动授权 `$to-spec`、`$domain-modeling` 或 `$to-tickets` 调和契约的路径。

相关历史记录可以保留用于审计，但不得由 4.3.0 重新解释为活动状态。

## 安装升级

从 Repo-local Marketplace 更新后，必须新建 Codex 任务，新的 Skills 和元数据不会可靠地注入已经打开的旧任务。

维护者本地候选安装使用 Plugin Creator 的 cachebuster 流程；正式源码与 GitHub Release 保持严格版本 `4.3.0`。
