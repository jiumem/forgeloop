# Forgeloop 4.3.0 发布候选

状态：源码门禁、authenticated Agent evaluation、本地候选安装与新任务回读已通过，并已取得创建 Release PR、合并、Tag、GitHub Release 和最终 Codex 安装的明确授权。只能从 Release PR 合并后的最终 `main` Commit 发布。

## 发布范围

- `$run-initiative` 由一个 Delivery Worker 负责 Slice 规划、实现、Finding 处置、最终 Gate、PR 与 Tracker 收尾，不再创建 Supervisor 或 Coder 子任务。
- 一个大 Ticket 或正式 Spec 使用一条交付分支、每个 Slice 一个逻辑 Commit、一次双轴 Review、一个最终 Gate 阶段和一个 PR。
- 一个有界 Initiative 逐 Spec 交付，每个 Spec 各有一条分支和一个 PR，并跨成员 Spec 复用同一组隔离 Reviewer。
- Slice 实现阶段不运行正式 Review 或完整 Gate；完整分支仅 Review 一次，Finding 由 Worker 处置为 `FIXED`、`REJECTED` 或 `CONTRACT_BLOCKER`，修改后的 Head 不再送审。
- `$spec-standards-review` 移除 400 字报告上限，完整检查冻结范围，只报告会改变当前交付判断的实质问题。
- 小型直接 Ticket 转普通实现；一次运行拒绝组合多个 Initiative。
- 旧 `run-initiative/references/`、Scheduler/Coder 修复循环、Checkpoint Event、Acceptance Seal 与累计审计运行协议已从活动插件和验证套件删除。

## 验收标准

- 入口：Manifest、README、Skill 元数据和发布配置统一回读为 `4.3.0`。
- 核心行为：大 Ticket、正式 Spec 和有界 Initiative 路由正确；小 Ticket 与多个 Initiative 保持边界。

- 交付：完整仓库 Gate 只在 Finding 处置后运行；PR 修复遵循仓库规则且不重新打开 Review。
- 恢复：只依赖 Tracker、Git、PR 与当前检查事实，不重建旧运行状态机。
- 发布：Release PR 合并后，Tag、GitHub Release 和最终 `main` Commit 精确一致；安装缓存来自已发布内容。

## 发布命令

只在 Release PR 合并且发布内容与 `origin/main` 一致后执行：

```bash
release_commit="$(gh api repos/jiumem/forgeloop/commits/main --jq .sha)"
gh release create v4.3.0 \
  --repo jiumem/forgeloop \
  --target "$release_commit" \
  --title "Forgeloop 4.3.0" \
  --notes-file docs/releases/4.3.0-release-notes.md \
  --latest
```

Tag 必须指向 Release PR 合并后的最终 `main` Commit；不得从本地候选提交、未合并分支或旧验证 Head 发布。
