# Forgeloop 4.3.0

Forgeloop 4.3.0 从 `$run-initiative` 中移除了反复 Review 与修复的循环。现在由一个 Delivery Worker 从 Slice 规划到集成全程负责一条完整交付分支；两个 Review 轴只在最终 Gate 前运行一次，对完整交付做全面检查并选择性报告问题。

## 一个责任明确的交付 Worker

- `$run-initiative` 不再创建独立的 Supervisor 或 Coder 子任务；
- 一个明确足够大的 Ticket 使用一条分支、每个 Worker 规划的 Slice 一个逻辑 Commit、一次双轴 Review、一个最终 Gate 阶段和一个 PR；
- 一个正式 Spec 使用相同形态，把其 Tickets 作为单条分支上的实现 Slices；
- 一个有界 Initiative 为每个 Spec 分别使用一条分支和一个 PR，并在各成员 Spec 之间复用同一组相互隔离的 Spec Reviewer 与 Standards Reviewer 子任务；
- 小型直接 Ticket 交给普通实现流程；一次运行不能组合多个 Initiative。

## 没有审批循环的 Review

- Slice 实现期间不运行正式 Review、完整仓库 Gate、CI、集成检查或 PR 检查；Worker 仍可使用范围窄的本地反馈；
- 所有 Slice 就绪后，完整交付分支只接受一次双轴 Review；
- Reviewer 报告属于证据而非授权，不产生 `PASS`、`REPAIR_REQUIRED` 或合并许可；
- Delivery Worker 为每条 Finding 记录一个 `FIXED`、`REJECTED` 或 `CONTRACT_BLOCKER` 处置，且不会把修改后的 Head 再送回 Review；
- 已批准契约内若需要实质性重新设计，则以 `REPLAN_REQUIRED` 停止；若必须修改契约，则以 `CONTRACT_BLOCKER` 停止。

## 全面检查，选择性报告

`$spec-standards-review` 保留现有双轴结构与范围规则，但移除了 400 字报告上限。两个 Reviewer 都必须检查完整冻结范围，不能遗漏会影响本次交付的实质问题。报告只收录能够改变当前交付判断的问题，并排除样式偏好、缺少证据的代码异味、已由工具强制检查的问题、推测性的加固建议，以及批准运行模型以外的产品条件。

## 持久证据与最终交付

- 冻结的 Base/Head 与两份完整报告通过所选 Tracker 交付项已有的 Comment、Note 或记录界面持久化；
- 每条 Finding 的处置、修复 Commit、验证证据和结果 Head 都在最终 Gate 前持久化；
- 处置完成后运行完整仓库 Gate，随后创建一个 PR，并遵循仓库正常的 Integration Policy；
- 恢复只读取 Tracker 证据、Git 历史、已有 PR 和当前检查事实，不重建已移除的 Scheduler 状态机；
- 已声明的 `Release Boundary` 仍在 `$run-initiative` 权限范围之外；流程只报告它，不执行也不修改其外部 Tracking reference。

## 移除旧运行时

活动插件及其验证套件已移除旧 `run-initiative/references/` 协议、每 Ticket 的 Scheduler/Coder/Reviewer 循环、修复预算、Checkpoint Event、Acceptance Seal、累计审计流程，以及自动契约协调交接。

4.3.0 不解释仍在进行中的 4.2.x 运行。请保留其 Tracker 与 Git 证据，并使用 4.3.0 支持的交付形态重新启动。详见 [4.2.1 → 4.3.0 迁移指南](../migrations/4.2.1-to-4.3.0.md)。

## 验证

本次发布通过以下证据验证：严格套件校验、上游与 UI 元数据同步、4.3 运行时契约、跨 Tracker 规划 fixtures、全部 20 个 Skill 的 Skill Creator 校验、Plugin Creator 校验、Python 契约测试、已认证 Agent 路由评估、本地 Marketplace 安装、安装缓存对比，以及新任务冒烟检查。
